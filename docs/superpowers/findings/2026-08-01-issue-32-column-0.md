# Issue #32 — column 0 black / image shifted right one pixel: device-verified fix

**Date:** 2026-08-01 · **Device:** `.81` · **Branch:** `fix/issue-32-column-0`
**A/B RBFs:** `9c2b894` (main, before) vs `4d6557c` (fix, after) — one commit apart, same rig, same hour.

## Verdict: fixed, measured on hardware

The scanout output register was one `ce_pix` behind `de`. Registering the pixel outputs on `clk_vid`
instead puts them in phase. Device A/B confirms every predicted consequence reversed at once.

## Mechanism (RTL, confirmed against the timing generator)

`openbor_video_reader.sv` registered `r_out/g_out/b_out` on the **same** `ce_pix` at which `hcol` was
current, while `openbor_video_top.sv:186` drives `vga_de` undelayed (`assign vga_de = tim_de`). The
consumer captures the pins on the `ce_pix` edge where `de` is high, so it sampled the pixel written
one edge earlier:

* screen column 0 held the blanking value → **black**
* screen column *c* showed framebuffer column *c-1* → **shifted right one pixel**
* framebuffer column 287 was written on the last active edge, outside `de` → **never displayed**

`openbor_video_timing.sv` was checked and is not implicated: `de <= ~next_hblank & ~next_vblank` is
computed from the current `hcount`, so `de` is exactly in phase with `hcount`. The skew was entirely
the output register's.

## Fix

Register the pixel outputs on `clk_vid` rather than on `ce_pix`. The value for `hcol` settles within
one `clk_vid` of `hcol` advancing — ~8 `clk_vid` before the next sampling edge at the device's /9
`ce_pix` — so the pins at the edge that names column *c* carry column *c*. `hcol` and the sync
outputs are untouched, so the raster does not move and the OSD `h_adj`/`v_adj` offsets are unaffected.

The prefetch the issue suggested (`linebuf[hcol+1]`) was **not** taken: it has to latch column 0
during the last blanking pixel of the previous line, where `vcount` still names that line, so
`linebuf[{vcount[0],...}]` would read column 0 out of the wrong bank.

## Device A/B — `fabric_probe`, a known-geometry static frame

`tools/fabric_probe` (gmloader-next) clears the whole framebuffer to RGB565 (0,0,160) and draws one
magenta triangle with vertices (160,48) (224,176) (96,176). Game killed, probe holding the frame,
one screenshot per RBF. Measured by `data/2026-08-01-issue32-column0-device-ab/probe_geom.py`:

| | column 0 | fully-black columns | blue clear spans | widest magenta scanline (y=175) |
|---|---|---|---|---|
| **before** — main `9c2b894` | `(0,0,0)` | `[0]` | x=**1**..287 (287 of 288) | x=**97..224**, midpoint 160.5 |
| **after** — fix `4d6557c` | `(0,0,165)` | `[]` | x=**0**..287 (288 of 288) | x=**96..223**, midpoint 159.5 |

Everything moved left exactly one pixel and the 288th column came back. The triangle midpoint moving
159.5 ← 160.5 is the absolute-X evidence: the shift was in the output stage, not in the emitted
geometry.

## Sim gate

`fpga/sim/tb_reader_ddr.sv` gate (k). The pre-existing orientation check (c) compares
`u_reader.cur_pix` against `u_reader.hcol` — both internal nets — so it was structurally blind to a
phase error at the pins. Gate (k) is a mixer model: an `always @(posedge clk)` that reads the
**pre-edge** `r_out/g_out/b_out` when `ce_pix && de`, deriving the screen column from the timing
generator's `hcount`.

|---|---|---|---|
| before | 124414 / 124416 | 430 | 430 |
| after | 0 | 0 | 430 |

Full suite 55/55 PASS; M10K ramstyle gate 0 findings.
