# Issue #15 — row 214 shows row 0: the defect is created during SCANOUT, not by the producer

**Date:** 2026-07-31 · **Device:** `.62` · **RBF:** `MalditaCastilla_2509573.rbf` (Jul 31 15:42)
**Branch:** `diag/issue-15-row-214`

## Verdict: DDR-CLEAN — decisive

The DDR scanout framebuffer contains a **correct** row 214 at the same moment the screen shows row
214 as a byte-exact copy of row 0. `comp_fb_dma` and the compositor are exonerated. The defect lives
in `openbor_video_reader.sv` / the scanout path (Task 3, not Task 4).

## The symptom, stated correctly

**Row 214 displays row 0's content.** One description, two appearances:

- Lit row 0 (throne-room cutscene, in-game HUD): row 214 carries that content — `nb0=51` *and*
  `nb214=51` together.
- Letterboxed scenes (rows 0-3 a black margin): row 214 appears black between two fully lit
  neighbours — `nb214=0` while `nb213=nb215=287`.

A mid-investigation reading characterised this as "row 214 blanks" from letterboxed frames alone.
That was an over-correction — the throne-room frames show row 214 carrying row 0's actual pixels.
The issue's original framing was right.

## What has been ruled out

**The producer.** Paired measurement above.

**The reader's logic under ideal DDR latency.** `fpga/sim/tb_reader_ddr.sv` was extended (commit
`47224fc`) to orientation-check **all 216 active rows** of a full frame — it previously checked only
25 and explicitly excluded the last active line — plus a line-buffer bank-collision detector
(`lb_waddr[7]` vs `vcount[0]`, the check the issue asked for). Result: 62208 checks per armed frame
(288x216 exactly), both buffers, **0 orientation errors, 0 collisions, all 216 rows covered**. That
bench's DDR model answers reads the cycle after acceptance, with no arbiter contention.

**The issue's published `ST_CHECK_CTRL` hypothesis, as applied to today's RTL.** It argued the
frame-restart line-0 fetch is dispatched with no vblank gate and collides with row 214's display. On
current RTL that path is unreachable during active video:

1. `openbor_video_timing.sv:162` — `new_frame` pulses at `hcount == H_TOTAL-1 && vcount ==
   V_ACTIVE-1`, the **last pixel of line 215**, simultaneously with `vblank` (`:143-144`).
2. `openbor_video_reader.sv:540` — that pulse is the **only** setter of `new_frame_pending`.
3. `openbor_video_reader.sv:624-647` — `ST_IDLE` has no unconditional exit; it leaves only on
   `new_frame_pending`, `cart_write_pending`, `cart_size_pending`, or `beacon_pending`.
4. `openbor_video_reader.sv:959-963` — after the line-215 fetch (issued during line 214's hblank),
   `ST_LINE_DONE` parks the FSM in `ST_IDLE`.

So the restart chain always runs **inside vblank**, after rows 214 and 215 have both been scanned
out. The gate the issue said was missing exists; it is in `ST_IDLE`, not `ST_CHECK_CTRL`.

## What that hypothesis was missing — and why it may still hold for the ORIGINAL build

In the reader at `ee13653`, the build all 11/11 evidence was captured on, `ST_IDLE:644` had
`else if (audio_wake) state <= ST_POLL_AUDIO_WR`, and **every** audio state exited to `ST_POLL_CTRL`
(`:1006, :1016, :1020, :1023, :1063, :1074`). `ST_IDLE` therefore *did* have a path to
`ST_CHECK_CTRL → ST_READ_LINE(line 0)` that does not wait for `new_frame`. The gate the refutation
above relies on did not exist then — commit `7980785` created it as a side effect of deleting the
audio FSM.

**Not established:** that this path selects row 214 specifically. The `ST_IDLE` window spans line
215, by which point row 214 is already scanned out. Trigger *class* confirmed; row selection not.
Do not treat this as the mechanism without a bench that reproduces it.

## Scanout-path changes since the original evidence (`ee13653..HEAD`)

Ranked by plausibility of affecting fetch timing vs active video, or reader DDR arbitration:

1. **`7980785`** (07-29) — deletes the reader's entire audio FSM (7 states, ~424 lines), moving audio
   to `gm_audio` on its own DDR channel. Its commit message: the audio path "shared the VIDEO
   scanout DDR master ... interleaved into the video FSM's idle windows."
2. **`a8512e5`** (07-29) — extracts `f2h_slot_mux`; the reader gains absolute DDR priority over the
   WORK→DDR copy, which could previously starve it ~158 µs (two scanlines).
3. **`5b84339`** (07-29) — audio refill burst 256 B → 1024 B while still on the reader's master.
4. **`dd33752`** (07-30) — inserts `ST_WRITE_SCANFRM` before `ST_POLL_CTRL`, adding one DDR write of
   delay ahead of the line-0 fetch. Adds margin, so wrong direction to be a cause.

Geometry (`FB_W`, `FB_H`, `FB_QW_BASE`) unchanged across the window. No commit in this range
mentions row 214.

## The instrument

`tools/fb_row_probe.c` — read-only `/dev/mem` probe, zero added FPGA-side DDR traffic (required:
`fpga/Maldita.qsf:31-37` records that `SOLARUS_DBG_PROBES` wedged the fabric). It mmaps
`FB_BASE 0x3BF40000` (`fpga/Maldita.sv:226`, `FB_QW_BASE = 29'h077E8000`), reads the control word for
the active buffer, copies rows 0/213/214/215 in one pass, then re-reads the control word and discards
the sample if the frame counter moved. Test A = row 214 identical to row 0 (needs a lit row 0);
Test B = row 214 all-black while 213/215 are lit (needs only lit neighbours). Verdicts state N and
carry a low-confidence qualifier below 8 usable samples.

**Why it reads the buffer actually on screen:** `openbor_video_reader.sv:443` exposes
`disp_active = active_buffer`; `comp_fb_dma.sv:198-219` only begins writing `~disp_active` once
`disp_active == published`, and only republishes after that write completes. So the DDR control word
and the reader's live `active_buffer` stay in lockstep — coherent, and never more than one
publish-to-poll gap ahead of the display, which is the window the post-copy recheck discards.

**Base-address validation:** the frame counter climbed and the `buf` bit alternated in every run,
confirming `FB_BASE` is correct for the loaded RBF and scanout is live.

## Black column 0 — separate defect, mechanism established

Present in **9/9** archived screenshots (exactly one black column) and confirmed downstream of DDR by
the `nb0=288` vs `nb0=287` pairing above. `openbor_video_reader.sv:1057-1082` registers
`r_out/g_out/b_out` on the same `ce_pix` at which `hcol` is current, so RGB lags `hcol` by one
`ce_pix`, while `openbor_video_top.sv:184` drives `vga_de` undelayed. At the first `de` pixel the
mixer samples the blanking value; screen column *c* shows framebuffer pixel *c-1*; framebuffer
column 287 is never emitted. No vertical term — it cannot produce a duplicated row. Fix separately.
