# Issue #15 — row 214 shows row 0: the defect is created during SCANOUT, not by the producer

**Date:** 2026-07-31 · **Device:** `.62` · **RBF:** `MalditaCastilla_2509573.rbf` (Jul 31 15:42)
**Branch:** `diag/issue-15-row-214`

## Verdict: DDR-CLEAN — decisive

The DDR scanout framebuffer contains a **correct** row 214 at the same moment the screen shows row
214 as a byte-exact copy of row 0. `comp_fb_dma` and the compositor are exonerated. The defect lives
in `openbor_video_reader.sv` / the scanout path (Task 3, not Task 4).

## The symptom, stated correctly

**Row 214 displays row 0's content.** One description, two appearances:

- Lit row 0 (throne-room cutscene, in-game HUD): row 214 carries that content — `nb0=51` *and*

- Letterboxed scenes (rows 0-3 a black margin): row 214 appears black between two fully lit

A mid-investigation reading characterised this as "row 214 blanks" from letterboxed frames alone.

## What has been ruled out

**The producer.** Paired measurement above.

**The reader's logic under ideal DDR latency.** `fpga/sim/tb_reader_ddr.sv` was extended (commit
`47224fc`) to orientation-check **all 216 active rows** of a full frame — it previously checked only
25 and explicitly excluded the last active line — plus a line-buffer bank-collision detector
(`lb_waddr[7]` vs `vcount[0]`, the check the issue asked for). Result: 62208 checks per armed frame
(288x216 exactly), both buffers, **0 orientation errors, 0 collisions, all 216 rows covered**. That
bench's DDR model answers reads the cycle after acceptance, with no arbiter contention.

## MECHANISM CONFIRMED — the issue's original hypothesis was right

> **Retraction.** An earlier revision of this document refuted the issue's `ST_CHECK_CTRL`
> hypothesis, arguing `ST_IDLE` gates the frame restart on `new_frame_pending` so the line-0 fetch
> can only land in vblank. **That refutation was wrong** and should not be reused. Its three errors:
> (1) it placed the `ST_IDLE` park during line 215 — the fetch runs a line ahead, so the park is in
> **line 214's hblank**; (2) it acknowledged `beacon_pending` as an `ST_IDLE` exit and dismissed it
> as harmless — it is the trigger; (3) it missed the two-frame dynamic below entirely.

Reproduced deterministically in simulation with **no injected delay and no injected event** —
`fpga/sim/sweep_reader_ddr.sh run +FRAMES=16` (commit `cef0b54`):

```
DIAG ROWDUP frame=11 row=214 shows ROW 0 (all 288 px), bank_src=0
DIAG SUM G=0 B=0 dup_events=1 dup_row=214 dup_frame=11 bad_rows=1 collide=0
         anchors=1 anchor_first=214 anchor_last=214 addr_errs=0 data_errs=0 frames=15
```

Across 19 frames × 216 rows, row 214 of frame 11 is the **only** row that displays anything other
than itself, and it displays all 288 pixels of row 0. Frame 11 is where `beacon_tick` (2^22 cycles
≈ 10.53 bench frames) first wraps — the old bench stopped at frame ~10, one frame short.

### Frame N — the beacon displaces the restart

1. `vc=214, hc=288` (hblank at end of row 214): last fetch of the frame issued, `display_line=215` →
   bank 1.
2. `vc=214, hc=308`: `ST_LINE_DONE` sees `display_line == V_ACTIVE-1` and parks in `ST_IDLE` —
   **during line 214's blanking**.
3. `beacon_pending` is set, and `ST_IDLE` takes it immediately:
   `ST_IDLE → ST_BEACON → ST_POLL_CTRL → ST_WAIT_CTRL → ST_CHECK_CTRL`.
4. `ST_CHECK_CTRL` → `display_line <= 0` → `ST_READ_LINE`. **Nothing gates this on vblank.** At
   `vc=214, hc=330` the burst lands: bank 0 now holds line 0. Harmless *this* frame — row 214 is
   already scanned out and row 215 reads bank 1.
5. The frame boundary arrives while the FSM is in the fetch loop, so `new_frame_pending` latches and
   is **not** consumed. Frame N+1 therefore runs at `display_line == vcount + 2`.

### Frame N+1 — the displaced restart lands on row 214

6. Two lines ahead, `display_line` reaches 215 at the end of **row 213**, so `ST_LINE_DONE` parks in
   `ST_IDLE` at `vc=213`.
7. The latched `new_frame_pending` fires there → the writeback chain → `ST_CHECK_CTRL` →
   `display_line <= 0` → `ST_READ_LINE`. At `vc=213, hc=331` the burst completes. **Bank 0 holds
   line 0 and nothing rewrites it before row 214 is scanned.**
8. `vc=214`: the display reads `linebuf[{vcount[0]=0, hcol[8:2]}]` = bank 0 = line 0. **Row 214 is
   byte-identical to row 0.**
9. At the `new_line` ending row 214 the re-anchor applies (`1 < 215 < 216`) → `display_line = 215`,
   so row 215 is fetched and correct, and the +2 phase self-heals.

One beacon fire → exactly one frame with exactly one wrong row.

### Why row 214 specifically

- **Bank parity:** `lb_waddr = {display_line[0], beat}` vs read bank `vcount[0]`, so a line-0 fill
  can only be seen by an **even** row.
- **Pacing:** after the displacement the `ST_IDLE` park sits at the end of row 213 — the only fill
  slot row 214 reads — and the next `new_line` re-anchors to 215, so the fetch for 214 is never
  issued and bank 0 is never overwritten.

### Rate, and what `7980785` actually did

`beacon_tick` is 22 bits on `ddr_clk` (98.4375 MHz) → one fire per 42.6 ms against a 16.688 ms
frame ⇒ **~39% of frames** carry the defect. That matches the device's 2-of-4 lit-row-0 screenshots.
The "1 in 40 overall" figure counts frames where the duplicate is *invisible* because row 0 and row
214 hold the same content (both in the black margin).

On `ee13653`, `ST_IDLE:644` had `else if (audio_wake) → ST_POLL_AUDIO_WR` with every audio state
exiting to `ST_POLL_CTRL`. `audio_wake` fires far more often than 42.6 ms, so nearly every frame took
the displaced restart — hence **11/11**. Commit `7980785` (audio FSM deleted) **did not fix this
defect**; it only removed the more frequent trigger, dropping the rate from ~100% to ~39%.

## Scanout-path changes since the original evidence (`ee13653..HEAD`)

Ranked by plausibility of affecting fetch timing vs active video, or reader DDR arbitration:

1. **`7980785`** (07-29) — deletes the reader's entire audio FSM (7 states, ~424 lines), moving audio
   to `gm_audio` on its own DDR channel. Its commit message: the audio path "shared the VIDEO
   scanout DDR master ... interleaved into the video FSM's idle windows."
2. **`a8512e5`** (07-29) — extracts `f2h_slot_mux`; the reader gains absolute DDR priority over the
   WORK→DDR copy, which could previously starve it ~158 µs (two scanlines).
3. **`5b84339`** (07-29) — audio refill burst 256 B → 1024 B while still on the reader's master.
4. **`dd33752`** (07-30) — inserts `ST_WRITE_SCANFRM` before `ST_POLL_CTRL`, adding one DDR write of
   delay ahead of the line-0 fetch. Adds margin, so wrong direction to be a cause.

Geometry (`FB_W`, `FB_H`, `FB_QW_BASE`) unchanged across the window. No commit in this range
mentions row 214.

## The instrument

`tools/fb_row_probe.c` — read-only `/dev/mem` probe, zero added FPGA-side DDR traffic (required:
`fpga/Maldita.qsf:31-37` records that `SOLARUS_DBG_PROBES` wedged the fabric). It mmaps
`FB_BASE 0x3BF40000` (`fpga/Maldita.sv:226`, `FB_QW_BASE = 29'h077E8000`), reads the control word for
the active buffer, copies rows 0/213/214/215 in one pass, then re-reads the control word and discards
the sample if the frame counter moved. Test A = row 214 identical to row 0 (needs a lit row 0);
Test B = row 214 all-black while 213/215 are lit (needs only lit neighbours). Verdicts state N and
carry a low-confidence qualifier below 8 usable samples.

**Why it reads the buffer actually on screen:** `openbor_video_reader.sv:443` exposes
`disp_active = active_buffer`; `comp_fb_dma.sv:198-219` only begins writing `~disp_active` once
`disp_active == published`, and only republishes after that write completes. So the DDR control word
and the reader's live `active_buffer` stay in lockstep — coherent, and never more than one
publish-to-poll gap ahead of the display, which is the window the post-copy recheck discards.

**Base-address validation:** the frame counter climbed and the `buf` bit alternated in every run,
confirming `FB_BASE` is correct for the loaded RBF and scanout is live.

## Black column 0 — separate defect, mechanism established

Present in **9/9** archived screenshots (exactly one black column) and confirmed downstream of DDR by
the `nb0=288` vs `nb0=287` pairing above. `openbor_video_reader.sv:1057-1082` registers
`r_out/g_out/b_out` on the same `ce_pix` at which `hcol` is current, so RGB lags `hcol` by one
`ce_pix`, while `openbor_video_top.sv:184` drives `vga_de` undelayed. At the first `de` pixel the
mixer samples the blanking value; screen column *c* shows framebuffer pixel *c-1*; framebuffer
column 287 is never emitted. No vertical term — it cannot produce a duplicated row. Fix separately.

## Next step — the fix

The defect is a **frame restart dispatched from `ST_CHECK_CTRL` while the display is still inside
active video**. The fix must prevent the line-0 fetch from landing in a bank the display is about to
read, without eating the line-0 preload slack (`preloading <= 1'b1`, `fifo_aclr_cnt <= 4'd8` at
`openbor_video_reader.sv:877-878`) that exists so row 0 is filled in time.

Constraints any candidate must satisfy, all now checkable in sim:
- `sweep_reader_ddr.sh run +FRAMES=16` must report `dup_events=0 bad_rows=0`.
- `+BEACON_ROW=<r> +BEACON_FRAME=5` must stay clean for **every** `r` (12/12 injection points).
- No new underflow: `anchors` must not rise, and rows 0/1 must stay correct.
- The DDR delay knobs (`+DDR_G`, `+DDR_B`) must not reintroduce it.

Note the same displacement can be reached by any path that services work from the `ST_IDLE` park —
the beacon today, `audio_wake` historically. Prefer a fix that makes the *restart* safe over one that
suppresses a particular trigger, or the next feature to hang work off `ST_IDLE` reintroduces it.

**Regression test already exists and needs no injection:** extending the standard bench past frame 11
turns `tb_reader_ddr` into a failing gate. It was deliberately left at the shorter frame count so the
suite keeps its 55-pass baseline until the RTL fix lands; extend it as part of the fix.

## Metric note

The issue's `dist()` — undefined in its body — is **mean absolute per-byte difference** over the 864
bytes of a row, not a mismatch count. Definition preserved at
