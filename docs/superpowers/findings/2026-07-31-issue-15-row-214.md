## What was built

- `tools/fb_row_probe.c` — read-only `/dev/mem` probe. mmaps the ship
  framebuffer region (`FB_BASE 0x3BF40000`, `fpga/Maldita.sv:226`
  `FB_QW_BASE = 29'h077E8000`), reads the control word to find the active
  buffer, copies rows 0/213/214/215 out of that buffer in one pass, then
  re-reads the control word and discards the sample if the frame counter
  moved (tear guard). Adds zero DDR traffic from the FPGA side.
- `tools/Makefile.fb_row_probe` — armhf cross-build via
  `gmloader-armhf-build:bullseye`, modelled on
  `tools/Makefile.audio_ring_probe`.

One deviation from the plan's verbatim source, authorized by the team lead:
the header comment's `docker run --rm ... bullseye \` line had a trailing
backslash inside a `//` comment, which real GCC (the armhf cross-compiler)
flags as `-Wcomment` (a backslash-continued `//` line looks like it might be
forming a multi-line comment; Apple clang's `cc` does not flag it). Fixed by
putting the whole command on one comment line. Both builds are now
warning-clean:

```
$ make -f tools/Makefile.fb_row_probe ARCH=native
cc -O2 -std=gnu11 -Wall -Wextra -o tools/fb_row_probe.native tools/fb_row_probe.c
$ docker run --rm -v "$PWD:/src" -w /src gmloader-armhf-build:bullseye \
    make -f tools/Makefile.fb_row_probe
arm-linux-gnueabihf-gcc -O2 -std=gnu11 -Wall -Wextra -mtune=cortex-a9 -o tools/fb_row_probe.armhf tools/fb_row_probe.c
```

## Why the probe reads the buffer actually on screen

The probe reads the control word's active-buffer bit from the ARM side and
trusts it to name the buffer the FPGA reader is currently scanning out. That
is not provable from the ARM side alone — it depends on the reader and
`comp_fb_dma` staying in lockstep, which is an RTL property:

- `openbor_video_reader.sv:443` — `assign disp_active = active_buffer;`. The
  reader exposes its own live active-buffer selection directly, with no
  separate "what am I displaying" state to drift out of sync.
- `comp_fb_dma.sv:198-219` — the write-start gate only lets `comp_fb_dma`
  begin writing the back buffer (`~disp_active`) once
  `disp_active == published`, i.e. once the reader has actually swapped onto
  the buffer `comp_fb_dma` last published. It only re-publishes an updated
  control word *after* that write finishes.

So the DDR control word (what the probe reads) and the reader's live
`active_buffer` (what is actually being scanned to the display) are held in
lockstep by construction — `comp_fb_dma` structurally cannot get ahead of the
reader. The only place they can diverge is the narrow window between a
vblank publish and the reader's next poll of the new control word, and that
is exactly the window the probe's post-copy coherence recheck (re-reading
`ctrl` after the four row copies and discarding the sample if it changed)
already exists to exclude. So a sample the probe reports as usable is, by
this RTL property plus the recheck, provably a sample of the buffer that was
on screen.

## Phase 1 refutation (carried forward from the plan, so it isn't re-derived)

The issue's published hypothesis — that `ST_CHECK_CTRL` restarts at
`display_line <= 0` with no vblank gate, clobbering bank 0 while row 214 is
being displayed — is refuted by static reading of
`fpga/rtl/openbor_video_reader.sv` and `fpga/rtl/openbor_video_timing.sv` at
`1072a4d`:

1. `openbor_video_timing.sv:162` — `new_frame` pulses at
   `hcount == H_TOTAL-1 && vcount == V_ACTIVE-1`, i.e. on the **last pixel of
   line 215**, simultaneously with `vblank` asserting (`:143-144`).
2. `openbor_video_reader.sv:540` — `new_frame_ddr` (the CDC'd pulse) is the
   **only** thing that sets `new_frame_pending`.
3. `openbor_video_reader.sv:624-647` — `ST_IDLE` has **no unconditional
   path onward**; it only leaves on `new_frame_pending`,
   `cart_write_pending`, `cart_size_pending`, or `beacon_pending`.
4. `openbor_video_reader.sv:959-963` — after fetching line 215 (issued
   during line 214's hblank), `ST_LINE_DONE` parks the FSM in `ST_IDLE`.

So the `ST_IDLE → ST_WRITE_JOY0 → … → ST_POLL_CTRL → ST_CHECK_CTRL →
ST_READ_LINE` chain that fetches line 0 of the next frame always runs
**inside vblank**, after rows 214 *and* 215 have both already been fully
scanned out. The gate the issue said was missing exists — it's in
`ST_IDLE`, not `ST_CHECK_CTRL`. Do not re-open the `ST_CHECK_CTRL` hypothesis
without new evidence; it does not match the RTL as of `1072a4d`.
