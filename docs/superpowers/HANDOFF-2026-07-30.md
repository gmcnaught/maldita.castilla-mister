## The two things most likely to bite a new session

1. **The frame cap must be a CAP, never a SYNC.** A classic vsync wait at an
   18 ms body against a 16.6882 ms scanout misses every window → ~30 fps, far
   worse than doing nothing. It is implemented as a leaky bucket, credit bounded
   to `[-1, burst-1]`. See [[gmloader-frame-cap-is-scanout-gated]].
2. **"Measured as negligible" is always conditional on the speed it was measured
   at.** Phase 2 explicitly tested the frame limiter, measured zero cost, and
   wrote "do not spend a lever on it." True at a 27 ms body, false at 18 ms —
   it was costing 1.6–1.7 ms. The systematic re-audit this prompted is
   `docs/superpowers/findings/2026-07-30-exposed-cost-audit.md`, which also
   *clears* several suspects so they need not be re-audited.

## The reframing that should shape Phase 4

Track host and fabric capability **independently**, with DDR not limiting either:

- **Track 1 (host production ≥60 fps):** host work ≈ 8–10 ms vs a 16.67 ms
  budget → already capable.
- **Track 2 (fabric processing ≥60 fps):** quiet 16.20 ms = **61.7 fps → already
  clears 60**. Arrival 21.37 ms = 46.8 fps → 1.28× short.
- **Track 3 (DDR):** must not artificially limit either.

**Therefore: on the quiet scene both tracks already individually clear 60 fps.**
The 55.6 delivered is the **1.89 ms of serialization between them**, not a
capability shortfall. The old `fabric ≤ 14.80 ms` gate was asking the fabric to
absorb the host's coupling cost. **Closing ~1.4 ms of coupling reaches 60 fps on
the quiet scene using the bitstream already deployed on `.62`.** The genuine
fabric gap is the arrival scene, where opaque cull is the only lever sized to
reach it (66 % quiet / 75 % arrival of covered px are opaque-occluded).

arbitration, the three f2h ports, the LW bridge):

## Device hazards that will waste your time if unknown

- **Frame-1 fabric wedge — now ~1 in 13 core loads (7.7 %), was ~1 in 2.**
  maldita PR #23 root-caused and largely fixed it (~6.5×); **a residual remains,
  it is not eliminated.** A retry clears it; **a reboot does NOT.**
  `mister_run.sh` auto-detects (`submit timeout`), retries up to 3×, and re-greps
  the pulled log post-hoc — a post-hoc hit **exits non-zero**, so a wedged run
  cannot be mistaken for a clean one. Keep that gate on: it is what caught the
  one wedge in the validation session.
- **`.62` is the TEST device; `.81` is PRODUCTION.** `deploy.py --host` still
  defaults to `.81` — always pass `--host 192.168.20.62`, or use the Makefile
  (`HOST` defaults to `.62`, `.81` needs `PROD=1`).
- **Engine deploy = swap then kill:** scp to `gmloader.new`, `mv -f` over the
  running binary, `killall -9 gmloader` — the handler re-execs it. **Never
  hand-launch after**, that is how you get two engines on one control block.
