# Native 288×216 display mode — design

**Date:** 2026-07-27
**Status:** Approved (sections reviewed in-session)
**Repos affected:** gmloader-next (host + mfgpu refmodel/sim), maldita.castilla-mister (production RTL), mister-gmloader (submodule bumps only)

## Problem

The core scans out 320×240 while Maldita Castilla renders internally at **288×216** — established by three independent sources: the GEN8 header (`defaultWindowWidth/Height`), all 71 rooms and every view/camera viewport, and a 400-frame on-device UV capture (app surface = 288×216 region in a padded 512×256 GL page). The marketing claim of 256×224 does not match the GameMaker build.

Because GM is told its window is 320×240, it stretches the app surface by exactly **10/9 in both axes** through the nearest-neighbour composite, duplicating every 9th column and row (the "10:9 upscale unevenness"). Additionally, the display timing is actually 320×**224** active (Genesis H40/V28) while the DDR reader's framebuffer is 240 rows tall, so **the bottom 16 framebuffer rows — the bottom ~14 game rows after the stretch — are never displayed** (documented in-tree at `openbor_video_reader.sv:830-834`).

## Goal

Pixel-perfect presentation on both outputs (the .81 HDMI bench unit and the .62 analog/tri-sync CRT unit): one resolution end to end, 288×216, with nothing rescaling anywhere between the game and the MiSTer scaler. Both the duplicated-pixel shimmer and the bottom-row crop disappear structurally.

Decisions made during brainstorming:
- **Shrink the host↔fabric framebuffer wire contract to 288×216** (not a scanout-window overlay on a 320×240 FB).
- **Uniform /9 horizontal timing** for the 288-wide raster.

## End state and data flow

- **Game side:** `MISTER_WIDTH/HEIGHT` become 288×216. GM is told its window is 288×216 — matching its GEN8 default and every room/view — so the application surface is 288×216 and GM's own composite quad becomes a 1:1 blit (`screen=[0,0..288,216]`). The 10:9 stretch disappears at the source; no interception or rect-rewriting. The floor-sampling convention (gmloader-next#20) makes the 1:1 fetch texel-exact.
- **Fabric contract:** `BLT_FB_WIDTH/HEIGHT` = 288×216 across all three lockstep copies (refmodel, RTL, sim). `FB_QWORDS` 19,200 → 15,552; row stride 80 → 72 qwords (576 bytes). DDR scanout buffers shrink to 124,416 B; base addresses and the 0x40000 buffer spacing stay put, so VSYNC/DIAG placement is untouched.
- **All three render paths stay comparable:** GL-readback, SW rasterizer, and fabric all natively produce 288×216 frames (pbuffer, `frame_capture`, `native_video_writer`, fabric DMA move together), so A/B benching remains apples-to-apples — with ~19% fewer pixels everywhere, which should also shave the 48.9 ms capture-readback cap.
- **Video out:** 288×216 active; uniform /9 horizontal — 380 px/line × 9 = 3420 MCLK/line, preserving the 15.7 kHz H rate; active width 288×9 = 2592 MCLK = 48.3 µs ≈ the standard 47.7 µs console window, so the CRT picture lands at the familiar width. Vertical window recentered where 224 was (`V_FP` 10→14, `V_BP` 25→29, total stays 262 lines, 59.92 Hz). `VGA_DE` frames exactly the game's pixels; `VIDEO_ARX/ARY` stays 4:3, which 288×216 natively is.
- **What the user sees:** HDMI scaler receives true 288×216 — at 1080p, integer scaling is an exact 5× (1440×1080). The .62 CRT gets a standard-width 15.7 kHz raster.
- **OSD:** the "Vertical Crop (224p)" option is meaningless at 216 active lines and is removed. H/V position adjust stays.

## Verification plan (lockstep TDD)

1. **Refmodel first** — bump `BLT_FB_*`, re-run the parity battery. The app-surface constants in `raster_backend_test.cpp` (288×216 in a 512×256 page) now coincide with the FB dims; add one case asserting the full-frame composite is a bit-exact 1:1 copy (glyph-1to1-phase already locks the texel convention).
2. **Sim** — regenerate vectors at 288×216; lockstep sim battery re-baselined bit-exact against the refmodel.
3. **RTL** — mirror the edits, sim green, then a Quartus fit on the self-hosted Windows runner with an STA check. M10K savings may help the −0.385 ns tint-path slack, but the fit can shift either way; if it regresses, that is the fit-cycle already owed.
4. **Device** — engine binary and RBF deploy **together**, `deploy.py --engine` explicit, md5-verify both sides. The contract carries no version/magic handshake, so a mismatched pair renders geometry garbage silently — the paired deploy is the only guard. Gates:
   - UV log shows the composite quad arriving as `[0,0..288,216]`.
   - Title/intro text clean on .81 HDMI.
   - Width/centering and H/V-position adjust checked visually on the .62 CRT.
5. **Re-baseline the bench** — old .81 numbers are invalid at the new pixel count; one timed A/B run records the new GL/SW/fabric baseline (expect the readback cap to drop roughly with the −19% pixels).

## Risks

- **GM behavior assumption** — "tell GM 288×216 → 1:1 quad" is inferred from the GEN8 defaults; the UV-log gate in device step 4 is the proof. If GM still POT-pads the surface page, nothing breaks — the sub-region UV path already handles that.
- **No contract handshake** — stale RBF + new engine (or vice versa) fails silently as garbage. Mitigated by paired deploy + md5; a protocol geometry handshake is out of scope.
- **Verification depth** — the game does not progress past the intro (known separate host-side issue), so visual checks are title/intro only. Acceptable: resolution plumbing is scene-independent.
- **.62 SDRAM phase** — orthogonal to video timing; any garbage on .62 must be checked against the known board-specific phase issue before being attributed to this change.
- **Watchdog** — frame cadence stays 59.92 Hz; no interaction with the stale-frame watchdog.

## Out of scope

Protocol geometry handshake, MiSTer.ini vscale tuning on the units, the game-progress bug, Lever-1 perf work, the non-shipping blitter spike.
